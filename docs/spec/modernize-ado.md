# Azure Pipelines `modernize`: retired task versions

> **Status:** detection is approved (sections 1-4, 7 and the task, replacement and class columns of section 8): `trasloco modernize --check` is built from it. The rewrite rules are approved as the implementation oracle for `modernize --write`.


Normative for `internal/dialect/azurepipelines/modernize`.

This specification defines how `trasloco modernize` rewrites references to retired Azure Pipelines task versions in YAML pipelines and templates. It was authored independently of the implementation: the tables in section 8 and the vectors in section 10 are the oracle. Keywords MUST, MUST NOT, SHOULD and MAY are used as in `README.md`; `VERIFY:` marks a fact that no cited official source confirms (section 11).

Microsoft announced that the tasks listed in section 8 retire on **2026-10-15** (still runnable, with a non-failing retirement error) and are **removed on 2027-03-15** (references then fail with a blocking error) [RET]. `catalog/azure-pipelines/tasks.retirement.yaml` (73 entries) is generated from that page and has exactly the same entries as section 8.

Notation for sources: `[RET]` is the retirement page, `[CAT]` the pinned generated task catalog, `[o:Name@N]` the retired `task.json`, and `[n:Name@N]` the replacement `task.json`; all reference-style link targets are listed in section 14. Old `task.json` files are either in the pinned catalog commit `f1962f12fac2899b5d689967dda0d25523cc3ec4` or, for the "legacy built-in" tasks that the repository no longer carries, in the public git history of `microsoft/azure-pipelines-tasks` under `Tasks/<Name>/task.json` (older, unversioned directory layout), pinned by commit SHA. Where neither exists the row says "old task.json not public".

## 1. Purpose and scope

1. `modernize` reads one YAML file at a time (a pipeline or a template of any kind), finds `task:` steps that reference a retired task version, and either rewrites the reference to the recommended replacement or reports why it cannot. It parses with the structure reader of `ado-yaml-structure.md`; it does **not** expand templates, so a template is rewritten in its own file, regardless of which pipelines include it.
2. Only the 73 retired task versions of section 8 are in scope. Other deprecated or old task versions (for example `Maven@3`) are left alone. Classic build and release definitions, task groups, pipeline decorators and Marketplace extension tasks are out of scope.
3. The tool changes text only where a row of section 8 allows it. It MUST NOT infer a mapping, MUST NOT contact the network and MUST NOT write the catalog.
4. The schedule is that of Azure DevOps Services [RET]; Azure DevOps Server availability of the replacement majors is not established (VERIFY: V19).

## 2. Safety principles

| ID | Principle |
|---|---|
| S1 | **No silent behaviour change.** Every rewritten step produces exactly one `TRL-MOD-0001` (class A) or `TRL-MOD-0002` (class B) diagnostic; every step that is not rewritten but references a retired task produces one of `TRL-MOD-0003`..`0006`, `0009`. |
| S2 | **Minimal diff.** The output is the input text with byte-range splices (section 6). The AST printer MUST NOT produce the output: it drops comments and normalizes layout (`ado-yaml-structure.md` section 15), which contradicts the plan sentence "AST rewrite + existing printer". Comments, blank lines, quoting, key order and line endings outside the edited ranges are preserved. |
| S3 | **Idempotent.** Running `modernize` on its own output changes nothing and reports no rewrite diagnostics. This holds because no replacement of section 8 is itself a retired entry (checked for all 73 rows, no chains). Class C/D steps and guard failures are reported again on every run, unchanged. |
| S4 | **Default deny.** An input of the retired task that the row neither passes through nor handles explicitly makes the step needs-manual (section 5.4). |
| S5 | **Literal values only.** A value is translated only when it is a literal scalar. A macro `$(x)`, a template expression `${{ }}` or a runtime expression `$[ ]` in a value that needs translation is needs-manual. Values that pass through unchanged may be anything. |
| S6 | **Class C and D steps are never edited.** The diagnostic carries the official recommendation. |
| S7 | **Failure isolation.** A guard failure affects only its step; all edits of that step are discarded, other steps in the file are still rewritten. |
| S8 | **Self-check.** After applying the edits the tool re-parses the result. Parse failure, a different number of steps, or any node outside the edited ranges that differs from the input is `TRL-INT-0002` and no file is written. |
| S9 | **Determinism.** Same input and same catalog give byte-identical output and diagnostics (ordering per `diagnostics.md` section 4). |
| S10 | **What the oracle can and cannot show.** The classes were derived from `task.json` facts (input names, aliases, types, defaults, options, visibility rules). Runtime behaviour of a new major that is not visible in `task.json` is not verified (VERIFY: V1); this is why every rewrite is reported, never silent. |

## 3. Recognising task references

### 3.1 Where

A step is a mapping that has a `task` key whose value is a scalar. Keys are matched case-insensitively (`ado-yaml-structure.md` 2.6). Steps are found in: root `steps`, `steps` of jobs, deployment lifecycle hooks, stage-less shapes, bodies of `${{ if }}`, `${{ elseif }}`, `${{ else }}` and `${{ each }}` directives, and in free-form values of `parameters` (template call sites, `extends`, and the `default` of parameters of type `step` or `stepList`) when the mapping has a `task` scalar and every other key is one of `inputs`, `displayName`, `name`, `condition`, `continueOnError`, `enabled`, `env`, `timeoutInMinutes`, `retryCountOnTaskFailure`, `target`. A step with `enabled: false` is treated like any other step.

### 3.2 Reference forms

The grammar is that of `ado-yaml-structure.md` section 12: `Name@Version` or `GUID@Version`, with `Version` = `N`, `N.M` or `N.M.P`. The retirement lookup key is the pair (task identity, major `N`). Source: [TASKS] ("specify the major version by using `@`", "full task version number after the `@`").

1. **Name form.** The name is compared case-insensitively with the `task` column of section 8. `copyfiles@1`, `COPYFILES@1` and `CopyFiles@1` are the same reference. The replacement is written in the canonical spelling of section 8.
2. **Full version.** `CopyFiles@1.1.4` is treated as major 1. The replacement is written as a major only (`CopyFiles@2`) and `TRL-MOD-0011` is added. VERIFY: V15 (whether a full version pins exactly that version).
3. **GUID form.** A GUID is compared case-insensitively. The identity is resolved with the pair (GUID, major): the candidates are the entries of section 8 whose GUID column equals the GUID and whose major equals `N`. Exactly one candidate means a retired reference. No candidate means the reference is not a retired task (for example `5bfb729a-a7c8-4a78-a7c3-8d717bb7c13c@2` is the live `CopyFiles@2`): there is no rewrite and no diagnostic, so a same-GUID replacement is inert on the second run. Two or more candidates (several retired tasks with the same GUID and major) mean no rewrite and `TRL-MOD-0005`. Several tasks share a GUID: `333b11bd-d341-40d9-afcf-b32d5ce6f23b` is `NuGetInstaller@0`, `NuGetRestore@1` and the live `NuGetCommand@2`; a bare-GUID lookup by "lexically first name" (`catalog.md`) is therefore insufficient and MUST NOT be used for retirement. The rewritten reference keeps the GUID and changes only `@N` when the replacement has the same GUID; otherwise it is written in name form and `TRL-MOD-0008` is added. Count method: of 73 rows, 56 replacement cells name exactly one task; 54 of those have both the retired GUID in section 8 and the replacement GUID in [CAT], and 39 of those 54 pairs have equal GUIDs. The implementation performs that comparison, rather than embedding the count.
4. **Namespaced names.** A name that contains a `.` (for example `publisher.extension.CopyFiles@1`) is an extension-contributed task, not the built-in. It is never rewritten. If its last segment equals a retired name (case-insensitive), `TRL-MOD-0010` (info) is reported. VERIFY: V14 (the naming scheme of extension task references is not described on [TASKS]; the page only says a custom task whose name equals a built-in one resolves to the built-in, and that a custom task can be referenced by its GUID).
5. **Dynamic references.** A value that contains `${{`, `$(` or `$[` is not static: no edit, `TRL-MOD-0005`. A reference without `@`, with an empty name or a malformed version is the parser's `TRL-PARSE-0015`; the file is not modified.
6. **Strings that look like references.** A scalar in `parameters` (pipeline-level, template declarations including `default` and `values`, template call sites) or in `variables` whose whole trimmed text is a retired reference (name or GUID form) is not edited and is reported with `TRL-MOD-0005`, because the tool cannot know where the string is used (for example `task: ${{ parameters.taskName }}`). Mappings that are steps by 3.1 are not strings and are rewritten.

### 3.3 Rewriting is decided per step

For each recognised retired step the tool looks up its row in section 8 and applies the class rules of section 4. Two retired steps in one file are independent (S7). Order of evaluation is source order.

### 3.4 Output of `modernize --check`

`--check` only reports; it never edits. Files are first classified: a YAML file is examined only if it parses and has one of `task`, `steps`, `jobs`, `stages`, `extends`, `template`, `trigger`, `pool`, `pr`, `resources`, `variables`, `parameters`, or a directive key (`${{ ... }}`) at the top level, or has a `task:` key anywhere. A document whose top level has `on` or `apiVersion` is excluded even when it contains a nested `task:` key, because those keys mark GitHub workflows and Kubernetes manifests. A file that does not parse is examined only if a line looks like a `task:` key. Other YAML files are skipped silently. A step is any mapping with a scalar `task` key (the key allowlist of 3.1 applies only to free-form `parameters` values); a step whose `task` key comes from an expression is reported with `TRL-MOD-0005`.

- **Exit codes.** 0 when there is nothing actionable (or `--check` is absent), 5 when `--check` finds an actionable result, 64 for a usage error, 1 when a named path cannot be read or, with `--strict`, when an examined file does not parse. Parse problems of examined files are warnings and do not change the exit code otherwise. Only results of severity `warning` or `error` are actionable; `info` results (`TRL-MOD-0010`) are listed as notes.
- **Text.** One block per result: `path:line:col  Retired -> Replacement  [label]`, the action, and `More: <page>`. Labels: `drop-in replacement` (A), `replacement with input changes` (B), `manual migration` (C), `no replacement` (D), `manual check` (`TRL-MOD-0005`). Notes come last, then one summary line. Paths are relative to the current directory.
- **JSON.** `{"findings": [...], "warnings": [...], "filesScanned": n, "filesSkipped": n}`; the arrays are never null. A finding has `code`, `severity`, `path`, `line`, `column`, `retiredTask`, `class`, `replacements`, `action`, `sourceUrl`, `help` (the documentation page of the task) and `diagnostics`. A warning has `code`, `severity`, `path`, `line`, `column`, `message`.
- **SARIF 2.1.0.** `artifactLocation.uri` is a percent-encoded relative reference with `uriBaseId` `%SRCROOT%`. Level: `error` for class D, `warning` for other actionable results, `note` for info. Parse warnings are `toolExecutionNotifications`.

## 4. Classes

Classes are data (column "Class" of section 8). The implementation MUST NOT recompute them. The criteria below explain how they were assigned from the cited `task.json` files.

| Class | Meaning | Action | Diagnostic | Fidelity |
|---|---|---|---|---|
| A | Same task family (the replacement is the same task at a newer major), every input of the retired version exists in the replacement with the same name or alias, the same type, the same value domain (the replacement may add options) and the same default; every input that is new in the replacement is optional with an inert default, or is required with a default that selects exactly the retired task's only behaviour. Explicit new-only inputs still fail closed under 5.5. | Change only the task reference (E1). | `TRL-MOD-0001` (warning) | exact |
| B | The replacement is a single task (same family, or a documented single-task successor), but at least one input is renamed, translated, removed, or has a different default, or a new input has a default that changes what the task does. Every such difference is listed in the mapping column. | Apply the mapping (section 5), then E1. | `TRL-MOD-0002` (warning) with the changes and the `review` items in `params` | approximated |
| C | The documented replacement is a different task, more than one task (the tool never splits a step into several), a task with a different input surface, or the old `task.json` is not public so that no mapping can be documented. | No edit. | `TRL-MOD-0003` (warning) with the official replacement and the reason | needs-manual |
| D | There is no replacement task: the platform or product is retired (Xamarin, App Center, Azure Cloud Services), the project is archived, or Microsoft points to an external tool or a script. | No edit. | `TRL-MOD-0004` (error) with the summarized official guidance | needs-manual |

Class A and B rows never need a human decision when no guard fires; a guard failure (section 5.4) turns the step into needs-manual with `TRL-MOD-0006` and no edit.

## 5. Mapping language (class A and B)

Every section 8 cell begins with one backtick-delimited mapping program. The prose after it is evidence, not executable syntax. Class C/D programs carry the exact diagnostic reason or guidance token but never authorize an edit. Input facts are from [CAT] for majors present there and otherwise from Appendix A and the pinned `task.json` references in the row.

### 5.1 Grammar

The grammar is EBNF. One U+0020 separates displayed terminals; identifiers are ASCII and case-sensitive in the table. JSON strings use RFC 8259 escapes and decode to Unicode strings; `null` is the JSON null value, not the string `"null"`.

```ebnf
program      = "pass" | operations | "manual ", qstring | "guidance ", qstring ;
operations   = operation, { "; ", operation } ;
operation    = rename | map | invert | drop | pin | add | guard | require | literal | review ;
rename       = "rename ", ident, " -> ", ident ;
map          = "map ", ident, " { ", pair, { ", ", pair }, " }" ;
pair         = qstring, " -> ", qstring ;
invert       = "invert ", ident, " -> ", ident ;
drop         = "drop ", ident, [ " if ", condition ] ;
pin          = "pin ", ident, " = ", value, [ " if ", condition ], [ " unless ", condition ] ;
add          = "add ", ident, " = ", value ;
guard        = "guard ", ( condition | "multiline(", ident, ")" ) ;
require      = "require ", ident, [ " if ", condition ] ;
literal      = "literal ", ident ;
review       = "review ", ident, " ", ( "default = ", value | "type ", qstring, " -> ", qstring ) ;
condition    = ident, ( " = " | " != " ), qstring ;
value        = qstring | boolean | integer | "null" | "K1" ;
ident        = letter, { letter | digit | "_" } ;
qstring      = ? RFC 8259 JSON string ? ;
boolean      = "true" | "false" ;
integer      = [ "-" ], digit, { digit } ;
letter       = "A" | ... | "Z" | "a" | ... | "z" ;
digit        = "0" | ... | "9" ;
```

The 73 programs in section 8 are the entire allowed program set; an unknown operation, non-canonical spacing, invalid JSON string or class/program mismatch is a specification error and MUST make catalog loading fail. `pass` is valid only for A. `operations` is valid only for B. `manual` is valid only for C and `guidance` only for D.

### 5.2 Matching, literals and conditions

1. Input names and aliases are compared case-insensitively; the first source occurrence supplies spelling and anchor. Duplicate case-insensitive keys make the step needs-manual with reason `duplicate-input` for every occurrence after the first.
2. *Present* means a key exists in the original `inputs` mapping, including a null value. Null decodes to the empty string for comparisons (VERIFY: V17). A *literal scalar* is a plain, single-quoted, double-quoted or block scalar whose decoded value contains none of `${{`, `$(` or `$[`. A mapping, sequence, alias, or scalar containing any of those markers is non-literal. Block scalars are literal subject to that rule (VERIFY: V13).
3. `K = "V"` is true only when K is present, literal and its decoded value equals V under Unicode simple case folding. `K != "V"` is true only when K is present, literal and unequal. If K is present and non-literal, evaluating either comparison fails closed with reason `non-literal-condition`; it never evaluates true or false. If K is absent, both comparisons are false. `unless C` is true when C is false because its input is absent or a different literal; it also fails closed when C is non-literal.
4. `multiline(K)` is true when K is present, literal and its decoded value contains U+000A or U+000D. A non-literal K fails closed with reason `non-literal-condition`.
5. Values in `map`, `invert`, `drop ... if`, `guard`, conditions controlling `pin`/`require`, and `literal` MUST be literal when present. Thus macros, template expressions and runtime expressions cannot bypass a guard. Pass-through values may be dynamic.

### 5.3 Operations

| Operation | Semantics |
|---|---|
| `rename A -> B` | Rename the matched old key to canonical B (E2); preserve its value. |
| `map K { "a" -> "b" }` | For present literal K, case-insensitively map listed decoded values and leave other literal values unchanged. |
| `invert A -> B` | Rename A to B and replace literal `true`/`false` case-insensitively with `false`/`true`; another value fails with `invalid-boolean`. |
| `drop K [if C]` | Delete K (E6) always or when C is true. If conditional K is present and C is false, it is unhandled and fails with `removed-input`. |
| `pin K = V ...` | When conditions allow and K is absent, append canonical K with encoded V. If K is an old input already present, preserve it and do not pin. If K is new-only and present, fail with `new-input-collision`, even when its value equals V. |
| `add K = V` | K MUST be new-only. Append it when absent. If it is present, fail with `new-input-collision`, even when equal. |
| `guard C` | When C is true, fail with `guard-condition`; a non-literal operand fails as specified in 5.2. |
| `require K [if C]` | When applicable and K is absent, fail with `required-input`; when K is present its value passes through. |
| `literal K` | Fail with `non-literal-input` when present and non-literal. |
| `review K default = V` | No edit. Add `{kind,input,value}` to `params.review`, with kind `default`; V is a JSON string, boolean, integer or null according to its grammar token. |
| `review K type "A" -> "B"` | No edit. Add `{kind,input,from,to}` to `params.review`, with kind `type`. |

`K1` decodes to the three-line string `{`, `"Content-Type":"application/json"`, `}` joined by U+000A, without a final newline. Its YAML insertion is the block scalar in E10.

### 5.4 Evaluation and edit order

1. On the original step, resolve layout and duplicate keys, then evaluate operation preconditions and the default-deny rules. Collect failures in source-key order, de-duplicate identical `(input,reason)` pairs, report every failure, discard all edits for that step, and do not emit the row's rewrite diagnostic.
2. If safe, apply operations by phase, retaining table order within a phase: `drop`; `rename`; `map` and `invert`; `pin` and `add`. `guard`, `require`, `literal`, `review` and `pass` do not edit. Then apply E1.
3. `params.changes` follows actual edit order and contains only edits performed. `params.review` follows program order and is present even when empty.

### 5.5 Default deny, new-only inputs and layouts

1. A present old input not accepted by the replacement and not consumed by `drop` fails with reason `removed-input`.
2. A present replacement input that is neither an old name/alias nor the source of `rename`, `pin` or `add` is *new-only* and fails with reason `new-only-input`. `review` does not authorize it. A `pin`/`add` target collision uses `new-input-collision`. This rule applies to A and B and prevents ignored old-task keys from becoming active after rewrite.
3. A key known to neither task is preserved and produces `TRL-MOD-0007`; it does not satisfy or collide with an operation.
4. An `inputs` template directive or dynamic key makes both A and B needs-manual with `TRL-MOD-0009`, reason `dynamic-input-key`, because it can hide a denied key. A flow-style mapping is allowed for A when all keys are static, because A edits only the task reference; it is `TRL-MOD-0009`, reason `flow-inputs`, for B. A non-mapping `inputs` value fails with reason `invalid-inputs`.

## 6. Edit rules

| ID | Rule |
|---|---|
| E1 | Task reference: replace only the reference text inside the scalar. Quote style, a trailing comment and surrounding spacing are preserved. Name form becomes the replacement `Name@Major` (canonical case); GUID form keeps the GUID and changes the version when the replacement has the same GUID (section 3.2.3). |
| E2 | Key rename: replace only the key text; quotes around a key are preserved. |
| E3 | Value change: replace only the scalar token. For `map`, preserve plain/single/double quote style; single-quote when the mapped text cannot be represented in the old style. A mapped block scalar becomes a single-quoted one-line scalar and the edit consumes its indicator and all continuation lines. For `invert`, write plain lower-case `true` or `false`. |
| E4 | Append: new lines are inserted after the last non-comment content line of the `inputs` mapping (including the nested lines of its last entry), at the indentation of the first entry of `inputs`, in pin order. |
| E5 | Create `inputs`: when the step has no `inputs`, insert `inputs:` after the last non-comment content line of the step mapping at the column of the step's keys, followed by the pinned entries one indentation unit deeper (the unit is the file's first observed nested indentation, default two spaces). |
| E6 | Delete: remove an entry from its first character to the end of its last line (including block scalar continuation lines and a trailing comment on those lines). Comment-only lines before it stay. If no entry remains, `inputs:` is removed too. |
| E7 | Line endings: inserted lines use the dominant line ending of the file (LF if tied). The state of the final newline is preserved. |
| E8 | All edits are computed against the original positions and applied from the end of the file backwards; edits never overlap; inserts at one offset keep pin order. |
| E9 | Unknown nodes, anchors, merge keys and multiple documents are the parser's errors (`TRL-PARSE-*`); the file is then left unmodified. |
| E10 | Appended qstrings are single-quoted YAML scalars (embedded `'` is doubled); booleans and integers are plain canonical tokens. `K1` is `|-` followed by its three lines, each one indentation unit deeper than the new key. `null` is valid only in `review` and is never written. A changed block scalar may become a one-line scalar under E3; deletion always includes all continuation lines. |

## 7. Diagnostics

Diagnostics use the model of `diagnostics.md`. Positions refer to the input file. The codes are registered in `internal/diag/registry.yaml`; `TRL-CAT-0002` (retired task, replacement used) remains the code of `convert`. Ordering is `(line, column, code)`. `modernize --check` treats warning and error findings as actionable. Params are JSON values: task refs and operation names use canonical section 8 spelling; `input` preserves the user's spelling when a key is present and uses the program's canonical name when a required key is absent; arrays are always present and never null.

| Code | Emitted when | Anchor | `params` |
|---|---|---|---|
| `TRL-MOD-0001` | a retired task with a drop-in replacement is detected (warning) | task value | `from`, `to` |
| `TRL-MOD-0002` | a retired task whose replacement needs input changes is detected (warning) | task value | `from`, `to`, `changes[]`, `review[]` |
| `TRL-MOD-0003` | class C step | task value | `from`, `replacements[]`, `reason` |
| `TRL-MOD-0004` | class D step | task value | `from`, `guidance` |
| `TRL-MOD-0005` | dynamic reference, ambiguous GUID, or string that names a retired task | the value | `value` |
| `TRL-MOD-0006` | guard failure in a class A/B step (no edit) | offending input key; task value for an unconditional missing `require` | `from`, `input`, `reason` |
| `TRL-MOD-0007` | input unknown to old and new task, preserved | the key | `from`, `input` |
| `TRL-MOD-0008` | GUID reference replaced by a name | task value | `from`, `to` |
| `TRL-MOD-0009` | step layout cannot be edited safely (flow style, directive or dynamic key in `inputs`) | task value | `from`, `reason` |
| `TRL-MOD-0010` | namespaced task not rewritten although its last segment is a retired name | task value | `value` |
| `TRL-MOD-0011` | full version reference replaced by a major | task value | `from`, `to` |

Exact array element schemas:

- `changes[]`: rename `{"op":"rename","input":A,"to":B}`; map `{"op":"map","input":K,"from":a,"to":b}`; invert `{"op":"invert","input":A,"to":B,"from":boolean,"value":boolean}`; drop `{"op":"drop","input":K,"value":decodedOriginal}`; pin/add `{"op":"pin"|"add","input":K,"value":typedProgramValue}`. `decodedOriginal` is a string (null input becomes `""`).
- `review[]`: default `{"kind":"default","input":K,"value":typedProgramValue}`; type `{"kind":"type","input":K,"from":oldType,"to":newType}`.
- `TRL-MOD-0003.replacements` is the replacement list in section 8 order. Reasons are the exact `manual` token. `TRL-MOD-0004.guidance` is the exact `guidance` token.
- `TRL-MOD-0006.reason` is one of `duplicate-input`, `removed-input`, `new-only-input`, `new-input-collision`, `guard-condition`, `non-literal-condition`, `non-literal-input`, `invalid-boolean`, `required-input`. `TRL-MOD-0009.reason` is one of `dynamic-input-key`, `flow-inputs`, `invalid-inputs`.
- Multiple diagnostics for one step are ordered by anchor, then code, then reason. Rewrite diagnostics precede informational `0007`, `0008`, `0011` at the same anchor because code order is lexical. A failed step emits only failure/layout diagnostics, never `0001`, `0002`, `0007`, `0008` or `0011`.
- Array order and element member order are exactly the order shown above and in the vectors. JSON consumers MUST treat object member order as insignificant; producers and golden-vector serializers emit it as shown. String values contain decoded Unicode; JSON escapes control characters (including K1 line feeds as `\n`) and otherwise uses the shortest RFC 8259 form.

2. `tasks.generated.yaml` contains the old `task.json` for only 34 of the 73 retired versions. 3. The GUID `333b11bd-d341-40d9-afcf-b32d5ce6f23b` is shared by `NuGetCommand@2`, `NuGetInstaller@0` and `NuGetRestore@1`; the lookup rule "bare GUID resolves to the lexically first task name" (`catalog.md`) does not identify a retired reference; (GUID, major) does.
4. `QuickPerfTest@1` lists `AzureLoadTest@1`, which is not in `tasks.generated.yaml` (it is a Marketplace extension task).
5. `replacementKind: task` is used for rows whose official text is not a drop-in task: the Xamarin rows (project migration), `PyPIPublisher@0` (Twine plus a script), `ServiceFabricComposeDeploy@0` ("or a currently supported container deployment workflow"), `NuGetPackager@0`/`NuGetPublisher@0`/`NuGetRestore@1` (the page says "with the pack/push/restore command", which the catalog does not record), `AzureCloudPowerShellDeployment@1/@2` (a platform that is retiring).

7. The plan sentence for M2-B ("AST rewrite + existing printer") conflicts with `ado-yaml-structure.md` section 15, which says the printer does not preserve comments. Section 6 uses byte-range splices.
8. `tasks.retirement.yaml` stores replacements alphabetically (`AzureCLI@3` before `AzurePowerShell@5` for `AzureNLBManagement@1`); the page lists `AzurePowerShell@5` first. Immaterial because the row is class C.

|---|---|---|---|---|---|
| `TRL-MOD-0001` | warning | ex | - | Retired task with a drop-in replacement | Use the replacement task named in the report; the inputs are identical. |
| `TRL-MOD-0002` | warning | ap | - | Retired task whose replacement needs input changes | Use the replacement task and change its inputs as described in the report; test the pipeline. |
| `TRL-MOD-0003` | warning | nm | - | Retired task needs a manual migration | Use `replacements` and follow `action`; no automatic mapping is documented. |
| `TRL-MOD-0004` | error | nm | - | Retired task has no replacement task | Follow the official guidance in `action`. |
| `TRL-MOD-0005` | warning | nm | - | Task reference is not static or names a retired task as a string | Replace the retired task by hand where the value is used. |
| `TRL-MOD-0006` | warning | nm | - | Input cannot be migrated automatically | Change the input named in `params.input` by hand, then re-run. |
| `TRL-MOD-0007` | warning | ap | - | Input unknown to the retired task preserved | Check the input name for typos. |
| `TRL-MOD-0008` | info | ap | - | GUID task reference replaced by a task name | None; the replacement has another GUID. |
